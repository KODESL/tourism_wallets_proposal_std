About this contribution package

This deliverable presents the draft standards contributions produced in
Phase 2 of the fellowship. It turns the gap analysis of D1.1 and the
requirements of D1.2 into concrete artifacts written for specific
standards-development organisations. Six contributions are included,
spanning the three contribution types called for in the workplan: a
use-cases and requirements note, a requirements input, three technical
notes, and a profile proposal. Together they provide a dedicated
artifact for each of the five Phase-2 priority gaps identified in D1.1.

Each contribution is self-contained. It opens with a submission cover
block giving its target body, document type, status and
intellectual-property terms, and it is written in the idiom that the
receiving body expects — W3C-style use cases and requirements, ISO-style
requirements using the verbal forms of the ISO/IEC Directives, and
engineering technical notes. They can therefore be extracted from this
compendium and submitted individually. All are drafts offered for
discussion; none has yet been formally submitted. Where a contribution
sits at a seam between bodies (notably the credential–token binding
note), it is addressed to more than one venue and is intended to be
coordinated through liaison.

The contributions are intentionally non-custodial and vendor-neutral:
they reference existing standards as targets and alignment points and do
not mandate any specific ledger, wallet or product.

C1.1 Abstract and status

This document presents four tourism use cases and the requirements they
place on the Verifiable Credentials data model, and proposes that the
Working Group and Community Group consider (a) adopting the use cases,
(b) developing a tourism-entitlement credential profile, and (c)
incubating a credential–token binding pattern. It is non-normative
community input and does not change any W3C specification.

C1.2 Introduction

Verifiable Credentials 2.0 provide a mature, royalty-free basis for
user-controlled digital credentials. Tourism, however, places demands on
credentials that the deliberately generic data model does not address
directly: entitlements that are time- and venue-bound, verified at high
throughput and often offline, held on behalf of a group, and frequently
represented in parallel as ledger tokens. This input describes those
demands as use cases and requirements so the community can assess
whether a sector profile and a small number of extensions are warranted.
The work is positioned to interoperate with the EU Digital Identity
Wallet rather than to compete with it.

C1.3 Use cases

Each use case is given as a short background-and-need statement followed
by the requirements it raises. Full formal versions are in D1.2.

UC-A — Multi-entry city attractions pass

**Background and need.** A traveller holds a multi-day pass covering
several attractions, used over time, sometimes where connectivity is
poor, and shared within a family but not resold.

**Raises.** Platform-independent entitlement credentials;
time/venue-bound validity that can be evaluated offline; group holding;
non-transferability; privacy-preserving status.

UC-B — Cross-border multi-day transport entitlement

**Background and need.** A multi-operator, two-country transport
entitlement is checked by inspectors, sometimes offline, and must be
honoured regardless of issuing operator.

**Raises.** Coded, language-independent semantics; cross-border
verifiability; offline status; issuer trust at operator scale.

UC-C — Hotel check-in with minimal disclosure

**Background and need.** At check-in a guest proves identity, legal age
and a valid reservation, disclosing only what is necessary, in alignment
with the EUDI Wallet.

**Raises.** Selective disclosure; minimal attribute sets per purpose;
eIDAS-aligned issuer trust.

UC-D — Cross-border festival with group tickets

**Background and need.** One buyer holds a group’s tickets, redeemed at
the gate and again for on-site benefits, with resale constrained and
disputes resolvable.

**Raises.** Group holding; multi-step redemption; binding between a
credential and a ledger token (see C3); auditable, privacy-preserving
evidence.

C1.4 Derived requirements on Verifiable Credentials

The use cases imply the following requirements on the data model or on a
tourism profile of it (RFC 2119 key words):

- **R-W3C-1.** A tourism profile MUST define how an entitlement (ticket,
  reservation, access right, loyalty) is expressed as a credential type
  with the attributes the use cases require. (D1.2 TW-F-01.)

- **R-W3C-2.** An entitlement MUST be able to carry machine-evaluable
  validity constraints — a time window and a venue or scope — that a
  verifier can evaluate deterministically and offline. (TW-F-04.)

- **R-W3C-3.** Presentation MUST support selective disclosure of only
  the attributes required for a stated purpose. (TW-F-07.)

- **R-W3C-4.** The model SHOULD support a holder presenting entitlements
  bound to other beneficiaries, with verifiable linkage. (TW-F-06.)

- **R-W3C-5.** Status (revocation/suspension) SHOULD be checkable in a
  privacy-preserving and offline-tolerant way; Bitstring Status List is
  the natural basis. (TW-SP-04, TW-SP-02.)

- **R-W3C-6.** Where an entitlement also exists as a ledger token, a
  standard binding SHOULD allow a verifier to confirm both
  representations refer to the same entitlement (incubation item; see
  C3). (TW-F-03.)

C1.5 Proposed next steps for the Working Group

The contributor proposes that the community: adopt UC-A to UC-D into the
use-case material; open discussion on a TourismEntitlement credential
type and the expression of validity and venue scope; consider whether
group/delegated holding needs data-model support or can be met by
profiling; and incubate the credential–token binding pattern in the CCG,
with liaison to ETSI ISG PDL and ISO/TC 307. The contributor is
available to edit a use-case note and to provide a reference
implementation as evidence.

C2.1 Scope

This contribution specifies interoperability requirements for
representing and verifying tourism entitlements across
distributed-ledger and credential systems and across national borders.
It is offered as input to the interoperability framework (ISO/TS 23516).
It does not specify a ledger, a wallet, or a credential format; it
states the interoperability properties that conforming systems are
required to exhibit.

C2.2 References and terms

Normative references include ISO 22739 (vocabulary) and ISO 23257
(reference architecture); informative references include the W3C
Verifiable Credentials Data Model 2.0, the Chain Agnostic Improvement
Proposals (CAIP) for ledger-agnostic identifiers, and Regulation (EU)
2024/1183. The terms entitlement, holder, issuer, verifier, binding and
entitlement identifier are used as defined in D1.2, clause 3.

C2.3 Requirements

**INT-1.** The interoperability framework shall define a ledger-agnostic
identifier for an entitlement, such that the same entitlement can be
referenced independently of the system in which it is recorded.

**INT-2.** The framework shall define a verifiable binding between a
credential representation and a ledger-token representation of the same
entitlement, enabling a verifier to confirm equivalence without trusting
a single system (see Technical Note C3).

**INT-3.** An entitlement shall carry validity constraints (time window
and venue or scope) that a verifier can evaluate deterministically,
including without network connectivity.

**INT-4.** Cross-system verification shall not require the verifier to
use a specific ledger, vendor or proprietary interface.

**INT-5.** Entitlement semantics should be coded and
language-independent so that an entitlement issued under one national
scheme can be verified, unchanged, under another.

**INT-6.** Status information (revocation, suspension, redemption)
should be verifiable in a privacy-preserving and offline-tolerant
manner.

**INT-7.** The framework should define conformance criteria and a test
approach by which an implementation can be assessed against INT-1 to
INT-6.

C2.4 Note to ISO/AWI 7603

ISO/AWI 7603 (decentralized identity for the identification of subjects
and objects, developed in conjunction with W3C Verifiable Credentials)
is a natural home for the identity aspects of tourism wallets. The
contributor proposes that tourism be considered as an application
domain, and that the standard reflect two properties the sector
requires: that the holder shall retain sole, revocable control of keys
and credentials (non-custodial control), and that recovery after device
loss shall be possible without transferring custody to a third party.
These correspond to D1.2 requirements TW-TL-01 and TW-TL-02.

C3.1 Problem and design goals

A tourism entitlement is often represented twice: as a Verifiable
Credential, which carries issuer trust, selective disclosure and
revocation, and as a ledger token (for example an ERC-721 or ERC-6672),
which carries programmable transfer and on-chain redemption. No standard
ties the two, so an entitlement is forced into one representation and
loses the benefits of the other, and a verifier cannot confirm that a
credential and a token denote the same right. This note proposes a
verifiable, ledger-agnostic binding between the two representations.

Design goals: the binding shall be (1) ledger-agnostic — not tied to a
specific chain or vendor; (2) mutual — each representation commits to
the other; (3) issuer-authoritative — a verifier can confirm the same
issuer authored both; (4) offline-friendly — the credential alone
suffices for an entry decision, with token reconciliation deferred; (5)
privacy-preserving — the binding does not introduce a stable
cross-context identifier for the holder; and (6) economical — minimal
data is placed on-chain.

C3.2 Binding mechanism

The mechanism has four elements.

- **Entitlement identifier (EID).** A stable, ledger-agnostic identifier
  for the entitlement (for example a URN), generated per entitlement and
  not derived from holder identity.

- **Credential-to-token reference.** The credential carries the token’s
  ledger-agnostic locator using a CAIP-19 asset identifier, together
  with a cryptographic digest (a commitment) of the token’s canonical
  descriptor. This lets a verifier locate and check the token, but the
  credential remains usable offline without doing so.

- **Token-to-credential commitment.** The token carries, on-chain or in
  its token metadata, the EID and a digest of the credential (its
  identifier plus a hash of its canonical form) and the issuer
  identifier. Only a fixed-size digest is stored, keeping the on-chain
  footprint minimal and avoiding personal data on-chain.

- **Issuer-authority linkage.** The issuer’s DID is linked to the
  on-chain minting account so a verifier can confirm a single authority
  produced both representations — for example by the issuer publishing,
  in its DID document or a signed statement, the CAIP-10 account
  identifier of the minter (a did:pkh-style assertion).

C3.4 Verification procedure

A verifier performs the following steps; steps 3 to 5 are optional in
offline mode (see C4):

1.  Verify the credential’s signature and the issuer, per VC 2.0 and the
    securing mechanism in use.

2.  Read the EID, the bound-token locator and the token descriptor
    digest from the credential.

3.  Resolve the token via its CAIP-19 locator; confirm it exists and
    read its descriptor and state (for example ownerOf / userOf for
    ERC-721/4907, redemption state for ERC-6672).

4.  Confirm the token’s descriptor hashes to the digest carried in the
    credential, and that the token’s bound-credential digest matches the
    presented credential — establishing the mutual binding.

5.  Confirm the issuer’s authority over the minting account
    (DID-to-account linkage), so the same issuer authored both.

6.  Apply the entitlement decision using validity window, venue scope
    and status.

C3.5 Security and privacy considerations

Cloning and replay are addressed by holder key-binding in the
presentation (the holder proves possession of the key the credential was
issued to) and, for proximity presentation, a per-interaction nonce or
transcript. Forgery is addressed by the two independent signatures (the
credential signature and the on-chain minting authority) plus the mutual
digests. Privacy requires that the EID be per-entitlement and not a
stable identifier for the holder, that the on-chain commitment contain
no personal data (only digests), and that the bound-token locator be
presentable selectively, so a holder can decline to reveal the on-chain
link where it is not needed. The interplay with revocation is that
status is authoritative at the credential layer (Bitstring Status List);
the token state is reconciled where available but is not required for an
offline entry decision.

C3.6 Standards alignment and open questions

The mechanism aligns with the W3C Verifiable Credentials Data Model 2.0
and Bitstring Status List, the Chain Agnostic Improvement Proposals
(CAIP-2, CAIP-10, CAIP-19), the did:pkh approach to linking DIDs and
blockchain accounts, and the ERC-721, ERC-4907 and ERC-6672 token
behaviours. Open questions for the receiving bodies: the
canonicalisation rule for the token descriptor (so digests are
reproducible); whether the binding vocabulary should be owned by W3C
(credential side) or ETSI ISG PDL (token side), with ISO/TS 23516
referencing both; and whether the token-to-credential commitment should
be mandatory on-chain or permitted in token metadata.

C4.1 Problem and design goals

Tourism entitlements are verified at physical gates where connectivity
is often poor or absent and arrival is peaked. The dominant presentation
protocol, OpenID4VP, generally assumes connectivity at the moment of
presentation, while the mdoc family (ISO/IEC 18013-5) defines an offline
device-retrieval model for identity documents but not for tourism
entitlements. This note proposes an offline verification profile with
explicit assurance tiers, so operators can choose a defensible point on
the trade-off between freshness and availability.

Design goals: verification shall be possible with no connectivity at the
point of presentation; the staleness of any offline decision shall be
bounded and stated; verification shall not require per-presentation
network round-trips whose cost grows with the queue; and presentations
shall resist cloning and replay.

C4.2 Assurance tiers

| **Tier** | **What is checked offline** | **Bounded staleness** |
|:---|:---|:---|
| Tier 0 | Credential signature, validity window and venue scope; holder key-binding | None beyond the validity window |
| Tier 1 | Tier 0 plus status against a cached Bitstring Status List | Status no older than the cache freshness window |
| Tier 2 | Tier 0 with short-lived, frequently re-issued entitlements | Bounded by the entitlement lifetime |
| Tier 3 | Full online status and token reconciliation (see C3) | Real-time |

An operator selects a tier per scenario: a high-volume museum gate may
accept Tier 1, while a cross-border transport inspection may require
Tier 2 or Tier 3. The tier and its freshness parameters are part of the
entitlement’s acceptance policy.

C4.3 Verification procedure

7.  The holder presents the entitlement over a local channel (QR, NFC or
    Bluetooth Low Energy proximity), with a per-interaction nonce or
    session transcript.

8.  The verifier validates the credential signature using cached issuer
    trust anchors synchronised in advance from an eIDAS-aligned trust
    list.

9.  The verifier evaluates the validity window and venue scope locally,
    and checks status to the selected tier (cached status list for Tier
    1; lifetime for Tier 2).

10. The verifier checks holder key-binding to resist replay and cloning.

11. Where redemption applies, the verifier records it locally and
    reconciles it with the ledger or issuer when connectivity returns.

C4.4 Security and privacy considerations

Offline operation must not become a privacy regression: verification
shall not phone home, and local verifier logs shall retain the minimum
necessary and no more. Replay and cloning are addressed by holder
key-binding and the per-interaction nonce/transcript. The principal
residual risk is double-spend of a redeemable entitlement across two
offline verifiers before reconciliation; this is bounded by recording
redemptions locally and reconciling promptly, and by reserving
multi-redeemable high-value entitlements for higher tiers. Status
staleness is the explicit cost of Tier 1 and is bounded by the cache
freshness window, which should be short for high-value entitlements.

C4.5 Standards alignment and open questions

The profile aligns with ISO/IEC 18013-5 (and 18013-7 for the online
tier), SD-JWT VC with key binding, the W3C Bitstring Status List (for
cached status), and OpenID4VP (for Tier 3). Open questions: default
freshness windows per entitlement value band; a standard representation
of the acceptance policy (tier and freshness) inside the entitlement;
and the reconciliation protocol for offline redemptions, including
double-spend handling under eventual consistency.

C5.1 Problem and design goals

The EU Digital Identity Wallet is the European centre of gravity for
user-controlled credentials, but its Architecture and Reference
Framework is centred on identity (person-identification data) rather
than sectoral entitlements. A tourism entitlement — a museum pass, a
regional transport entitlement, a hotel reservation — is naturally an
electronic attestation of attributes (EAA), yet there is no profile for
issuing and verifying one through the EUDI ecosystem. This proposal
sketches such a profile so tourism entitlements can be carried in the
EUDI Wallet and verified by EUDI relying parties.

Design goals: a tourism attestation shall be expressible as an EAA (or a
qualified EAA where higher assurance is justified); it shall be issued
and presented using the ecosystem’s existing protocols; it shall support
selective disclosure and the data-minimisation profile of D1.2; and it
shall align with the binding and offline mechanisms of C3 and C4 where
the entitlement is also token-backed or verified offline.

C5.2 Attestation profile

The attestation carries a small, purpose-built attribute set,
expressible as an SD-JWT VC or as an mdoc attestation:

> // Tourism attestation — attribute set (illustrative)
>
> entitlement_type : "regional-transport-pass"
>
> entitlement_id : "urn:tw:eid:..."
>
> valid_from : "2026-06-01"
>
> valid_until : "2026-06-08"
>
> scope : \["zone-1", "zone-2"\] // coded, language-independent
>
> beneficiary_binding : "holder" \| "named" // group support
>
> transfer_policy : "non-transferable"
>
> issuer : "did:web:transport.example-region.eu"
>
> bound_token : { ... } // optional; see C3

A qualified EAA (QEAA) is proposed where cross-border legal reliance is
needed (for example, regional transport subject to inspection); a plain
EAA is sufficient for lower-risk entitlements such as an attraction
pass.

C5.3 Issuance and presentation

Issuance uses OpenID4VCI from the operator (acting as an attestation
provider) to the wallet. Presentation uses OpenID4VP to the venue or
inspector acting as a relying party, with selective disclosure so that
only the attributes required for the stated purpose are revealed. For
offline inspection, the presentation follows the offline profile of C4.

C5.4 Trust and assurance

Issuer and relying-party trust is established through the eIDAS trust
framework. Because tourism involves a very large and dynamic population
of issuers (operators) and relying parties (venues), the proposal flags
the need for a scalable registration mechanism — corresponding to D1.2
requirement TW-SP-03 — and recommends that ETSI TC ESI consider how
sector relying parties register at scale. Assurance level is matched to
entitlement risk, with QEAA reserved for entitlements requiring
cross-border legal reliance.

C5.5 Standards alignment and open questions

The proposal aligns with the EUDI Architecture and Reference Framework
(v2.4.0), OpenID4VCI and OpenID4VP, SD-JWT VC and ISO/IEC 18013-5. Open
questions for the expert group: whether tourism warrants a dedicated
attestation rulebook or can be accommodated by a generic EAA profile;
the threshold at which an entitlement requires a QEAA rather than an
EAA; and how sector relying parties register and are discovered at scale
across Member States.

C6.1 Problem and design goals

Selective disclosure is available technically — through SD-JWT VC and
through unlinkable cryptosuites such as BBS — but there is no agreed
answer to the prior question: for a given tourism purpose, which
attributes is a verifier entitled to request at all? Without agreed
minimal sets, each operator decides independently, which leads to
inconsistent privacy and routine over-collection at venues. This note
proposes a data-minimisation profile that defines minimal disclosure
sets per common tourism purpose and a machine-readable way to bind a
presentation request to a stated purpose.

Design goals: a verifier’s presentation request shall declare a purpose;
for each purpose there shall be a defined minimal attribute set and,
where possible, the request shall use predicates rather than raw
attributes; and a wallet shall be able to detect and warn when a request
exceeds the minimal set for its stated purpose.

C6.2 Purpose-to-attribute profile

The profile is a registry of purposes, each mapping to a minimal set of
attributes or predicates. The following entries are illustrative.

> // Purpose -\> minimal disclosure (illustrative)
>
> venue-entry : { entitlement_type, valid_now: \<predicate\>,
> venue_in_scope: \<predicate\> }
>
> age-check : { age_over: 18 } // predicate, not date_of_birth
>
> reservation : { reservation_ref, valid_now: \<predicate\> }
>
> transport-zone : { entitlement_type, zone_in_scope: \<predicate\>,
> valid_now: \<predicate\> }
>
> loyalty-status : { tier } // not full transaction history

A presentation request references a purpose; the wallet evaluates the
request against the purpose’s minimal set and surfaces anything beyond
it to the holder for explicit consent. The minimal sets are intended to
be co-defined with operators and data-protection authorities (an open
issue carried from D1.2).

C6.3 Predicates and unlinkability

Wherever a yes/no or range answer suffices — “valid now”, “within
scope”, “over 18” — the profile prefers a predicate over disclosure of
the underlying attribute, so that the verifier learns only the answer.
Because tourism involves many short interactions, the profile also
addresses correlation: it recommends unlinkable presentation where the
format supports it (for example BBS-based proofs) and, otherwise,
batch-issued single-use credentials, so that presentations at different
venues cannot be trivially linked by those verifiers. This corresponds
to D1.2 requirement TW-SP-02.

C6.4 Standards alignment and open questions

The profile aligns with SD-JWT VC selective disclosure, the W3C
Verifiable Credentials Data Model 2.0 and BBS-based unlinkable proofs,
the presentation-request mechanisms of OpenID4VP, and the data elements
of ISO/IEC 18013-5; its purpose is to operationalise the GDPR principles
of data minimisation and purpose limitation. Open questions: who
maintains the purpose registry and how it is versioned; the level of
predicate support that can be assumed across credential formats; and how
the profile aligns with EUDI relying-party registration, which
determines what a relying party is permitted to request.
